# Publishing

Each module of this repository is **versioned and released independently**:

- Kotlin Multiplatform modules (e.g. `features/Sample`) are published to [Reposilite](https://maven.infomaniak.app)
  (Android, JS klib and metadata variants) and, when they have a JS target, to an npm registry.
- The [`plugins`](../plugins) build is published to Reposilite as Gradle plugins (implementation jar + plugin markers).
  All the plugins share a single version.

Releases are driven by [release-please](https://github.com/googleapis/release-please) from
[Conventional Commits](https://www.conventionalcommits.org/). Snapshots are published on demand.

## Overview

| File                                                  | Role                                                                          |
|-------------------------------------------------------|-------------------------------------------------------------------------------|
| `release-please-config.json`                          | **List of the modules enabled for publishing** and release options.            |
| `.release-please-manifest.json`                       | Last released version of each module (updated by release-please).             |
| `<module>/gradle.properties`                          | `version` of the module (updated by release-please).                          |
| `<module>/CHANGELOG.md`                               | Changelog of the module (generated by release-please).                        |
| `build-logic/.../PublishConvention.kt`                | Convention plugin `com.infomaniak.multiplatform_core.convention.publish`.     |
| `plugins/build.gradle.kts`                            | Publishing of the Gradle plugins (mirrors the convention, see below).         |
| `.github/workflows/release-please.yml`                | Release PRs, tags, GitHub releases and publication of the released modules.   |
| `.github/workflows/publish-snapshot.yml`              | Manual publication of a snapshot of one module.                               |
| `.github/workflows/publish-npm.yml`                   | npm publication, called by the two workflows above.                           |
| `.github/workflows/cleanup-snapshots.yml`             | Weekly cleanup of old Reposilite snapshots.                                   |

Coordinates:

| Module           | Gradle (Reposilite)                                                    | npm                                     | Tag              |
|------------------|------------------------------------------------------------------------|-----------------------------------------|------------------|
| `features/Sample` | `com.infomaniak.multiplatform_core:sample:<version>`                  | `@infomaniak/multiplatform-core-sample` | `sample-<version>` |
| `plugins`        | `id("com.infomaniak.multiplatform_core.plugins.<plugin>") version "<version>"` | -                               | `plugins-<version>` |

The artifactId of a module is its lowercase project name (`sample`, `sample-android`, `sample-js`, …).

## Releasing

1. Merge pull requests with Conventional Commit messages into `main` (`fix:` → patch, `feat:` → minor, `feat!:` or a
   `BREAKING CHANGE:` footer → major; before 1.0.0, a breaking change bumps the minor version).
2. On every push to `main`, release-please opens or updates **one release PR per module** that has releasable changes,
   e.g. `chore(main): release sample 0.2.0`. A commit belongs to a module when it touches files under the module
   directory. Each created or updated release PR is published as a snapshot (`0.2.0-SNAPSHOT`, see
   [Snapshots](#snapshots)).
3. Merge the release PR of the module you want to release, whenever you want. The other release PRs stay open.
4. The `Release Please` workflow then tags the module (`sample-0.2.0`), creates the GitHub release, and publishes the
   module from the release commit to Reposilite (and npm).

Several release PRs can be merged together: each released module is published by its own matrix job.

### Forcing a version

Add a `Release-As: x.y.z` footer to a commit that changes at least one file of the module. An empty commit is
attributed to **every** module, so it would force this version on all of them.

```
chore(sample): release 1.0.0

Release-As: 1.0.0
```

### Changes outside of a module

Changes to shared build files (`build-logic`, `gradle/libs.versions.toml`, …) are not attributed to any module, so they
do not trigger a release. To release a module affected by such a change, push a commit that changes a file of the module
(e.g. its `CHANGELOG.md` or `README.md`), optionally with a `Release-As` footer.

### Dependencies between modules

A published module can only depend (`api`/`implementation` project dependencies) on modules that are published too:
`verifyPublishableDependencies` fails otherwise, and runs before every publication and in the PR checks. The POM of a
module references the version declared in the `gradle.properties` of its dependencies, so **release a dependency before
the modules that depend on it**.

## Enabling or disabling a module

`release-please-config.json` is the single switch.

To **enable** a module (e.g. `features/Foo`):

1. Apply the convention plugin in `features/Foo/build.gradle.kts`:
   ```kotlin
   plugins {
       id("com.infomaniak.multiplatform_core.convention.publish")
   }
   ```
2. Create `features/Foo/gradle.properties`:
   ```properties
   # x-release-please-start-version
   version=0.0.0
   # x-release-please-end
   ```
3. Add the module to `release-please-config.json`:
   ```json
   "features/Foo": {
     "component": "foo",
     "extra-files": [{ "type": "generic", "path": "gradle.properties" }]
   }
   ```
4. Add `"features/Foo": "0.0.0"` to `.release-please-manifest.json`.

The `release-config` PR check (`.github/scripts/check-release-config.sh`) verifies that these files agree.

To **disable** a module, remove it from `release-please-config.json` and `.release-please-manifest.json`: release-please
stops opening release PRs for it and the snapshot workflow refuses it. Its tags and published versions are kept.

## Snapshots

### Release PR snapshots (automatic)

Every time release-please creates or updates the release PR of a module, the `Release Please` workflow publishes a
snapshot of the upcoming version from the release PR branch, e.g. `0.2.0-SNAPSHOT` for `chore(main): release sample
0.2.0`. A release PR left unchanged by a push is not republished. This lets you test exactly what will be released
before merging the release PR.

### Manual snapshots

Run the **Publish a snapshot** workflow (Actions tab) on the branch to publish, with:

- `module`: a module of `release-please-config.json` (e.g. `features/Sample`, `plugins`);
- `version`: e.g. `0.2.0`, published as `0.2.0-SNAPSHOT` to `https://maven.infomaniak.app/snapshots`.

The npm package of a JS module is published as `0.2.0-snapshot.<run number>.<run attempt>` with the `snapshot`
dist-tag, since npm versions are immutable. Snapshots older than 15 days are deleted every week.

## Versions in the build

The version of a module is the `version` of its `gradle.properties`. It can be overridden for **this module only**
with `-Ppublish.version.<module path>=<version>` (`:` replaced by `.`), which is what CI does:

```bash
# Snapshot of features/Sample in mavenLocal
./gradlew :features:Sample:publishToMavenLocal -Ppublish.version.features.Sample=0.2.0-SNAPSHOT

# Gradle plugins in mavenLocal
./gradlew :plugins:publishToMavenLocal -Ppublish.version.plugins=0.2.0-SNAPSHOT

# npm package (build/dist/js/productionLibrary)
./gradlew :features:Sample:jsBrowserProductionLibraryDistribution
```

A non-snapshot override must equal the declared version (`verifyPublishVersion` fails otherwise), so a release can only
publish the version committed by release-please.

| Gradle property          | Default     | Description                                                   |
|--------------------------|-------------|---------------------------------------------------------------|
| `publish.version.<path>` | -           | Version override of one module.                               |
| `publish.npmScope`       | `infomaniak`| npm scope of the packages (`@<scope>/multiplatform-core-<module>`). |
| `publish.npmSnapshotId`  | `local`     | Suffix of npm snapshot versions.                              |

`plugins` cannot use the convention plugin (`build-logic` depends on `plugins`), so `plugins/build.gradle.kts`
duplicates its publishing configuration: keep both in sync.

## Consuming

### Gradle

```kotlin
// settings.gradle.kts
dependencyResolutionManagement {
    repositories {
        maven("https://maven.infomaniak.app/releases")
        maven("https://maven.infomaniak.app/snapshots") // Only for snapshots
    }
}

// build.gradle.kts
kotlin {
    sourceSets {
        commonMain.dependencies {
            implementation("com.infomaniak.multiplatform_core:sample:0.2.0")
        }
    }
}
```

### Gradle plugins

```kotlin
// settings.gradle.kts
pluginManagement {
    repositories {
        maven("https://maven.infomaniak.app/releases")
        gradlePluginPortal()
    }
}

// build.gradle.kts
plugins {
    id("com.infomaniak.multiplatform_core.plugins.ktlint") version "0.2.0"
}
```

### npm

```bash
npm install @infomaniak/multiplatform-core-sample            # latest release
npm install @infomaniak/multiplatform-core-sample@snapshot   # latest snapshot
```

The registry of the `@infomaniak` scope must be configured in the consumer's `.npmrc` if it is not npmjs.org.

## Repository configuration

| Name                    | Kind     | Description                                                                                  |
|-------------------------|----------|----------------------------------------------------------------------------------------------|
| `REPOSILITE_USERNAME`   | Secret   | Reposilite credentials.                                                                      |
| `REPOSILITE_PASSWORD`   | Secret   | Reposilite credentials.                                                                      |
| `GPG_KEY_ID`            | Secret   | Signing key id.                                                                              |
| `GPG_PRIVATE_KEY`       | Secret   | Armored signing key, with `#` instead of line breaks.                                        |
| `GPG_PRIVATE_PASSWORD`  | Secret   | Signing key password.                                                                        |
| `KCHAT_KMP_WEBHOOK_URL` | Secret   | Optional, KChat notification of snapshots.                                                   |
| `RELEASE_PLEASE_TOKEN`  | Secret   | Optional PAT or GitHub App token, so release PRs trigger the PR checks (`GITHUB_TOKEN` events do not trigger workflows). |
| `NPM_TOKEN`             | Secret   | npm registry token.                                                                          |
| `NPM_REGISTRY_URL`      | Variable | npm registry URL (e.g. `https://registry.npmjs.org`). **npm publishing is skipped while unset.** |
| `NPM_SCOPE`             | Variable | Optional, overrides the npm scope (`infomaniak`).                                            |
| `NPM_ACCESS`            | Variable | Optional, `npm publish --access` value (e.g. `public` for a public scoped package on npmjs). |

The "Allow GitHub Actions to create and approve pull requests" setting must be enabled for release-please.
